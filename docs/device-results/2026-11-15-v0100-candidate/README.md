# 0.10.0 candidate measurements — 2026-11-15

**Publication authorized with explicit 0.10.0 limitations; distribution gates pending.**
This report holds the device and performance evidence of the fourth 0.10.0 candidate.
- Asked on 2026-11-15 «Выпускать 0.10.0 с этими ограничениями и публиковать свидетельства?»,
  the owner answered «Да, публикуй».

  decisions and the accepted known limitations.

  only what the fourth candidate's changes touch («Только затронутое»). Every table below names
  the build behind each result.
- Every failed attempt of a counted run is kept under [failed/](failed/) with its cause.

- The documented criterion, physical footprint and threads at most 8 MiB and 8 above the
  baseline, passed: MASQUE +0.20 MiB and +0 threads, mKCP +0.23 MiB and +0 threads.
- 0.9.0's Apple bound on RSS was 8 MiB from the baseline. MASQUE's RSS grew 8.25 MiB
  (+0.86, +5.47, +5.55, +8.25 MiB over the recovery stages), 0.26 MiB over it.
- Without a re-run, on the owner's decision of 2026-11-15, the bound in this archive is
  Android's rule: max(8 MiB, 25% of the RSS after the first cycle's recovery), 9.63 MiB for
  MASQUE. **It was set after the measurement.**
- Measured as Android's rule measures growth, from the first cycle's recovery to the second's,
  MASQUE grew 2.78 MiB.

## Performance

Release builds on an Apple M-series Mac (macOS 27.2.1) with no other heavy load.
([build records](performance-builds/), [notes](performance-builds/NOTES.md)).

| Metric | Median | Threshold |
| --- | ---: | --- |
| process-throughput | 546.6 MiB/s | at least 10 |
| vless-encryption-throughput | 359.2 MiB/s | at least 272.7 (half of plain VLESS) |
| ip-on-demand-latency | 0.166 ms | at most 1.162 (direct + 1 ms) |
| xhttp-memory | 18.5 MiB | at most 64 |
| mkcp-throughput / latency / memory | 132.1% / 101.3% / 11.1 MiB | ≥50% / ≤200% / ≤64 MiB |
| masque-throughput / latency / memory | 155.1% / 87.7% / 12.8 MiB | ≥50% / ≤200% / ≤64 MiB |

- The first four come from [run-v06-feature-benchmarks.py](performance-features/).
- The mKCP and MASQUE rows are single-flow loopback SOCKS ingress, five rotating-order pairs
  against the pinned Xray-core's own client over a common Xray-core server
  ([comparisons](performance-protocols/protocol-comparisons.json)). Xray-core's client peaked
  at 59.8 MiB (mKCP) and 41.9 MiB (MASQUE).
- One mKCP pair measured 60.8% (mKCP moves a lot between repeats).
- [Comparison against 0.9.0](release-comparison/release-comparison.json): every protocol 0.9.0
  shipped, against a build of the `v0.9.0` tag, in one run, five repeats.
  - Throughput is within budget for all twelve (90.6–111.7% of 0.9.0), and so is p95 latency
    (90.9–107.0%).
  - Memory is above the 110% budget for ten protocols (111.2–117.7%), listed by id in the
    known limitations.

## Known limitations

The [decision record](../../releases/v0.10.0-owner-decisions.json) has each one in full, with
its numbers:
- the ten memory regressions against 0.9.0;
- the Android network change and lock-wake, not tested;
- the iPhone LAN runs made on the third candidate's build;
- a MASQUE or WireGuard tunnel's 16 TCP flows;
- MASQUE UDP datagrams above 1252/1232 bytes;
- MASQUE's one-flow download (11.8% of Xray-core's);
- mKCP's delayed remote close;
- iOS's sometimes slow first exchange after a tunnel start.
- the Apple RSS bound set after the measurement (MASQUE 8.25 MiB against 0.9.0's 8 MiB).

# `v0.4.1-rc.4` XHTTP Lifecycle Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Close the RC4 XHTTP lifecycle gaps with deterministic regressions for pre-commit H2 GOAWAY retry, post-commit non-replay, concurrent H2 close/write, and reusable packet-buffer ownership under cancellation.

**Architecture:** Keep retry policy at the XHTTP packet transport boundary, where pool checkout and request commitment are both visible. Classify only a remote GOAWAY returned before `H2Client::open_request` creates a request stream as retryable, require the refused checkout to have been pooled, retire only that H2 pool entry, and force at most one new connection. Treat every upload, response, reset, I/O, or post-commit failure as authoritative. Exercise cancellation with explicit channels and the existing H1 `PreparedRequest` reclamation seam; H2/H3 retain their copy-isolated packet input. Timeouts are deadlock guards, never scheduling mechanisms.

**Tech Stack:** Rust 2021, Tokio, `h2` 0.4, `bytes` 1, integration tests in `xray-transport`.

**Depends on:** [RC4 hardening design](../specs/2026-08-28-v0.4.1-rc.4-hardening-design.md).

**Followed by:** [scheduled compatibility](2026-08-28-v0.4.1-rc.4-scheduled-compatibility.md), [benchmarks and documentation](2026-08-28-v0.4.1-rc.4-benchmarks-and-docs.md), then [release orchestration](2026-08-28-v0.4.1-rc.4-release-orchestration.md).

- [ ] **Step 1: Add a client-frame observer used only by the new GOAWAY tests.**

Add `FrameObservedStream`, analogous to `RecordingIo` in
`stream_xhttp_h2_tests.rs`, around the client side of a `DuplexStream`. It must:

- forward `AsyncRead`, `AsyncWrite`, and `TransportStream` without changing bytes;
- accumulate complete client-written HTTP/2 frames after the 24-byte preface;
- send a one-shot notification when it observes the client's SETTINGS ACK;
- send a separate one-shot notification when it observes a PING ACK;

Use an internal byte buffer because one `poll_write` is not guaranteed to

```rust
const H2_PREFACE: &[u8] = b"PRI * HTTP/2.0\r\n\r\nSM\r\n\r\n";

const H2_SETTINGS_FRAME: u8 = 0x4;
const H2_PING_FRAME: u8 = 0x6;
const H2_ACK_FLAG: u8 = 0x1;
```

The notification sender is consumed with `Option::take`, so every milestone is
reported at most once.

### Task 3: Implement one fresh retry for a pooled remote GOAWAY before commitment

**Files:**

- Modify: `crates/xray-transport/src/stream/xhttp/h2.rs:39-60`

- [ ] **Step 1: Add a semantic classifier without changing the public error shape.**

Keep `H2Error::Protocol` unchanged so the existing lower-level H2 retirement
tests continue to match it. Add a crate-visible method instead:

```rust
impl H2Error {
    pub(crate) fn is_remote_goaway_before_request_commit(&self) -> bool {
        matches!(
            self,
            Self::Protocol { context, source }
                if matches!(
                    *context,
                    "connection is not ready" | "request HEADERS could not be sent"
                ) && source.is_go_away()
                    && source.is_remote()
        )
    }
}
```

The two context strings already identify errors returned by
`SendRequest::ready()` and `SendRequest::send_request()` inside `open_request`.
Do not classify upload, response, flow-control, reset, driver, or body-drain
errors. Re-run
`graceful_goaway_marks_the_client_dead_and_rejects_new_streams` after this
step; its `H2Error::Protocol` assertion must remain unchanged.

- [ ] **Step 2: Make one H2 pool entry explicitly retireable.**

Extend `ConnectionLifecycle`:

```rust
struct ConnectionLifecycle {
    active: AtomicUsize,
    retired: AtomicBool,
    last_idle: StdMutex<Instant>,
    clock: XhttpClock,
}
```

Initialize `retired` to `false`, add `is_retired` and `retire`, and record
whether the selected entry had already been used:

```rust
struct H2Checkout {
    client: H2Client,
    activity: ConnectionActivityLease,
    was_pooled: bool,
}

impl H2Checkout {
    fn retire(&self) {
        self.activity.lifecycle.retired.store(true, Ordering::Release);
    }
}
```

In `H2Pool::client`, remove retired entries in the existing `retain` call,
exclude them from the availability search, and set `was_pooled` from the
entry's `fresh` value before flipping `fresh` to `false`. Do not call
`XmuxClient::mark_closed` for the successful retry: that would retire the
entire xmux slot and discard unrelated healthy H1/H3 state.

- [ ] **Step 3: Add a force-new checkout path.**

Add `H2Pool::fresh_client` and `XmuxClient::fresh_h2_client`. This path must
dial and handshake a new H2 connection directly instead of searching
`state.connections`; after success it inserts that connection into the pool
with an activity lease already held and returns `was_pooled=false`. The newly
inserted `H2Connection` must already have `fresh: false`: this checkout has
consumed its first use, even though it bypassed the availability search. That
invariant makes the next checkout from this entry report `was_pooled=true`, so
a later independent packet may use the same narrowly scoped stale-pool retry.
A failed dial inserts nothing. The force-new path may not fall back to another
pre-existing pool entry.

- [ ] **Step 4: Loop only around checkout and request opening.**

In `send_h2_packet_inner`, leave body construction outside the loop. Build a
fresh `http::Request` per attempt, then return the successful checkout with the
exchange so its activity lease remains alive:

```rust
let exchange = async {
    let mut force_fresh = false;
    loop {
        let checkout = if force_fresh {
            client.fresh_h2_client(Arc::clone(&dial)).await?
        } else {
            client.h2_client(Arc::clone(&dial)).await?
        };
        let request = h2_request(&prepared.request, &self.endpoint, Some(body.len()))?;
        match checkout.client.start_streaming(request).await {
            Ok((upload, pending)) => return Ok((checkout, upload, pending)),
            Err(error)
                if !force_fresh
                    && checkout.was_pooled
                    && error.is_remote_goaway_before_request_commit() =>
            {
                checkout.retire();
                force_fresh = true;
            }
            Err(error) => return Err(XhttpTransportError::Http2(error)),
        }
    }
}
.await;
let (checkout, mut upload, pending) = match exchange {
    Ok(exchange) => exchange,
    Err(error) => {
        let _ = uploaded.send(Err(StoredFailure::from_error(&error)));
        return Err(error);
    }
};
let _activity = checkout.activity;
```

Preserve the existing upload-completion one-shot behavior on every terminal
path. A refusal on a never-used/fresh checkout is terminal; a refusal on the
forced replacement is also terminal. No loop may enclose `write_all`,
`shutdown`, `pending.open`, or response draining.

### Task 4: Pin concurrent public-stream close versus pending H2 write

**Files:**

- Modify: `crates/xray-transport/tests/stream_xhttp_transport_tests.rs`

- [ ] **Step 1: Write the race regression before changing production code.**

Add:

```rust
#[tokio::test]
async fn dropping_h2_packet_up_while_upload_is_flow_controlled_cancels_once_and_releases_pool()
```

Set `max_each_post_bytes` to 16 and use an eight-byte server receive window.
Wrap this test's client-side `DuplexStream` in the `FrameObservedStream` from
Task 1. Keep the server connection driver polled while the test waits for the
observer's client SETTINGS ACK; start the public writer only after that ACK,
so the client's send stream has definitely applied the server's eight-byte
window. The server then keeps the GET downlink open, accepts the POST, consumes
its first DATA without releasing capacity, and sends `post_blocked`. Both
server request streams report their reset reason through one
`mpsc::UnboundedSender<(Method, Reason)>`.

Split the public stream with `tokio::io::split`. Give each half a separate
oneshot cancellation receiver. The read task selects, with the cancellation
branch biased, between one downlink read and cancellation; the write task does
the same between `write_all(&[0x5a; 64])` and cancellation. Each task drops its
owned half and returns exactly one enum result, `Io(...)` or `Cancelled`, rather
than being aborted from outside. After the observed SETTINGS ACK, the 64-byte
write exceeds twice the 16-byte packet pipe capacity: the worker consumes the
first packet but can send only eight bytes, a second packet fills the pipe, and
the public write must remain pending. Prove this by waiting for both
`writer_started` and `post_blocked`, then requiring
`writer_done.try_recv()` to be empty.

Send both cancellation signals, join both tasks under `DEADLINE`, and assert
one terminal `Cancelled` result per direction. This makes destruction of the
logical stream race the already pending write without borrowing one stream
mutably from two tasks. Collect server events and assert exactly one terminal
`CANCEL` for the GET and exactly one for the POST; `try_recv` must report no
third reset.

Finally wait, using `yield_now` plus the outer deadline, until:

```rust
assert_eq!(transport.h2_connection_activity_counts().await, vec![0]);
```

Keep the scripted server connection accepting requests after both canceled
streams. Open a replacement flow, have the server accept its GET and POST,
return `200 OK`, exchange one packet and EOF, and complete both sides. Assert
the replacement succeeds and the dial count remains one. Local cancellation
must release leases but must not retire a healthy H2 connection.

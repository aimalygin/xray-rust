# `v0.4.1-rc.4` hardening design

Date: 2026-08-28
Status: proposed for implementation

## Context

`v0.4.1-rc.3` is published for both `xray-rust` and
`xray-rust-mobile`. The core tag passed the ordinary Rust, Go-oracle, Apple,
Android, secret, supply-chain, bounded-fuzz, and pinned-Xray interoperability
jobs. The mobile tag produced the expected XCFramework, standalone AAR,
licenses, manifest, and checksums without publishing a remote Maven
coordinate.

The release audit found no known hermetic-suite runtime failure, but it also
found that Phase 1 is not completely evidenced. Three XHTTP lifecycle
regressions named by the roadmap are missing or narrower than the roadmap
claim, publication-quality comparison results still target the previous
Xray-core baseline, the scheduled upstream-compatibility path is incomplete,
and several release/status documents no longer describe the published state.

`v0.4.1-rc.4` closes those release-confidence gaps. It is a hardening release,
not a feature release.

## Goals

1. Complete the specifically tracked XHTTP lifecycle regression set: HTTP/2
   GOAWAY retry boundaries, concurrent HTTP/2 close/write behavior, and
   reusable packet-buffer ownership across cancellation.
2. Publish fresh, reproducible release-mode comparison evidence against the
   exact Xray-core `v26.7.28` commit and the current stable sing-box release.
3. Add scheduled early-warning coverage without weakening the exact pinned
   release contract.
4. Reconcile roadmap, status, verification, and release instructions with the
   actual RC state.
5. Produce matching, checksum-bound `v0.4.1-rc.4` core and mobile GitHub
   prereleases, with no registry publication.

## Non-goals

- No new proxy protocol, stream transport, DNS transport, routing feature, or
  public management API.
- No selector groups, node health/failover, outbound chaining, DoH/DoT/DoQ,
  ABI capability discovery, VLESS post-quantum encryption, or IPv6 Fake IP.
- No claim of complete grpc-go byte parity, HTTP/3 performance parity,
  exhaustive fuzzing, sanitizer/Miri coverage, independent security audit, or
  full physical-device soak completion.
- No stable `v0.4.1` tag and no Maven Central/GitHub Packages publication as
  part of the RC4 operation. Stable promotion is a separate decision after RC4
  evidence is reviewed.

## Design decisions

### 1. XHTTP lifecycle regressions

The GOAWAY and close/write tests operate at the highest layer that can observe
pool selection, request commitment, stream cancellation, and connection
retirement together. Lower-level H2 tests remain useful for protocol mechanics
but are not enough to prove those transport behaviors. Buffer ownership is
pinned at the private production helper used by the packet worker because that
is the narrow seam where a completed request allocation re-enters reuse.

#### GOAWAY retry boundary

Add an end-to-end pooled-H2 regression with two branches:

- A stale pooled client that refuses a request before the request is committed
  may be retired and redialled once. The fresh connection receives the request
  exactly once.
- Once request bytes or body data may have reached the peer, the operation is
  not replayed. The caller receives a deterministic error and the stale client
  is retired.

The implementation must retain the current one-retry ceiling and must never
turn an ambiguous partial upload into an automatic replay.

#### Concurrent close and write

Add a deterministic test that holds an upload write pending while another task
shuts down or drops the public XHTTP stream. The test must prove bounded
completion, no task leak or deadlock, one terminal result per direction, and
correct pool retirement. Scheduling is coordinated with explicit channels or
barriers; arbitrary sleeps are not acceptance evidence.

#### Buffer lifetime under cancellation

Add a regression that cancels packet-up/body work while the H1 request owns its
reusable `PreparedRequest` buffer. The buffer must have one owner, be reclaimed
at most once, and never be returned to the reusable path until the request
future has released it. The test exercises the existing
`reclaim_packet_buffer` seam. H2/H3 keep their copy-isolated fixed input buffer
and do not hand that reusable allocation to the request future. Production
changes are limited to extracting the ownership boundary or the smallest fix
exposed by the regression.

All three tests are written before any corresponding production fix and must
fail for the intended reason if they expose a bug. Existing partial-write
non-replay, H2 retirement, gzip stream-local error, and H3 cancellation tests
remain unchanged.

### 2. Benchmark evidence

The active comparator contract remains Xray-core `v26.7.28` at
`5ca6f4b7d4dc20a881d4330e498892697627ec0c`. The sing-box comparator is the
current stable release at execution time and is recorded by exact version,
binary digest, build tags, and source revision when source-built.

The stable release resolved for this run is sing-box `v1.13.19`. Its REALITY
client reports `ClientVer` 1.8.1, which the pinned Xray-core server rejects
under the v26.7.28 default `minClientVer` 26.3.27. The scientific contract does
not weaken that fixture policy and does not inflate the timeout to disguise the
version rejection. Consequently `reality-vision-xudp` and
`reality-vision-bulk-throughput` are two-engine xray-rust/Xray-core series;
sing-box remains in every other common workload it supports. The resulting RC4
publication matrix is exactly 141 series and 705 embedded runs. The base task
contributes 27 summaries and 135 embedded runs.

Use release binaries and the existing process-level harness. Record at least
five runs for the supported common slices that back public claims:

- idle and 100/1000 held-flow RSS;
- direct TCP bulk throughput and reconnect behavior;
- VLESS + REALITY + Vision TCP and UDP/XUDP behavior between xray-rust and the
  pinned Xray-core server (stable sing-box is unavailable for this slice);
- WebSocket, HTTPUpgrade, and gRPC common stream workloads;
- XHTTP H1/H2/H3 against Xray-core, including the bounded XHTTP memory profile;
- geodata memory/routing where the existing harness provides equivalent input.

Every result group records host/OS, toolchains, command line, workload
parameters, engine revision or executable SHA-256, sample count, raw artifact
location, RSS, CPU/bytes where available, latency/loss where the harness
supports them, and any unavailable measurement explicitly. Historical
`v26.5.9` charts remain labelled and are not overwritten. New charts and tables
use a new date-labelled result group. Numbers are not published if provenance
validation fails or a workload is not semantically comparable.

A material unexplained regression blocks RC4 publication until fixed or
documented with a reviewed budget decision. Benchmark artifacts that are too
large or host-specific remain outside Git; the repository stores the reviewed
summary, commands, provenance, and chart inputs needed to reproduce published
claims.

### 3. Scheduled compatibility coverage

The exact pinned-Xray RC interoperability job remains blocking and unchanged in
meaning. Scheduled CI adds two early-warning slices:

1. A broader run against the same pinned reference, covering the ignored
   interoperability matrix and resource-oriented smoke that is too expensive
   for every merge.
2. A non-blocking focused smoke against Xray-core `main`.

The `main` smoke is never treated as the supported release contract and cannot
make a tagged RC pass. It records the tested upstream commit and exposes a
clear warning/failure in the scheduled run. Any revision override is explicit;
the ordinary pinned harness continues to reject the wrong commit. The focused
slice uses only loopback-generated credentials and public fixtures.

Long-running fuzz campaigns, sanitizers, Miri, and concurrency-model tooling
remain tracked follow-up work. RC4 retains the existing blocking bounded fuzz
gate.

### 4. Documentation and release engineering

Update documentation in the same core branch to:

- distinguish an implemented item from an outstanding roadmap item;
- record RC3 as published and RC4 as the active hardening candidate;
- use canonical DNS-outbound `Return`, while describing `Reject` only as a
  warned legacy alias;
- make the documented Rust test command match CI by excluding the fuzz package
  from `--all-targets`;
- clarify HTTPUpgrade early-data behavior, routing selectors, pinned-Xray
  verification, and the meaning of "stable" before `1.0`;
- retain the declared gRPC and H3 divergence boundaries.

Core stable publication remains an explicit later step. The mobile release
guide must state that repository Actions need permission to create pull
requests for the checksum-lock workflow. If that permission is intentionally
disabled, the documented fallback is to open the already-pushed checksum
branch as a PR manually; the workflow must fail with an actionable message
rather than silently claiming completion.

### 5. Versioning and publication sequence

Core sequence:

1. Land reviewed code, tests, CI, and benchmark-publication tooling; set every
   workspace package to `0.4.1-rc.4`, add the dated changelog entry, refresh
   the lockfile, and freeze a clean measurement candidate.
2. Measure that exact RC4 candidate. Commit only validated benchmark evidence
   and public documentation afterward; any other path change invalidates the
   measurements and returns to step 1.
3. Run the release validator on the clean reviewed tag source, create one
   annotated `v0.4.1-rc.4` tag, and push the branch/tag.
4. Require all core tag jobs, including pinned interop and bounded fuzz, to
   succeed before accepting the GitHub prerelease.

Mobile sequence:

1. Pin the exact core tag, commit, tree, lockfile, header, and module-map
   digests; update the mobile version to `0.4.1-rc.4`.
2. Build and lock the exact Apple artifact through the checksum branch/PR.
3. Run mobile CI, create the annotated matching tag, and require the release
   workflow to verify the XCFramework, standalone AAR, manifest, notices, and
   checksums.
4. Verify `remoteMavenPublication: false`, no Maven archive in the prerelease,
   and the Maven publication job is skipped.

Published tags are immutable. Any post-tag source, test, workflow, or artifact
fix uses `v0.4.1-rc.5`; tags are never moved.

## Error handling and safety

- XHTTP retry logic fails closed on ambiguous request commitment.
- New scheduled upstream checks cannot relax pinned release validation.
- Benchmark publication fails closed when comparator identity or provenance is
  incomplete.
- Release jobs verify tag objects, commits, asset digests, and expected asset
  sets before mutation.
- No secrets, routable fixture endpoints, or real user profiles enter tests or
  benchmark artifacts.

## Verification

Local/core verification includes:

- focused red/green XHTTP regression tests;
- `cargo fmt --all -- --check`;
- `cargo clippy --workspace --all-targets --all-features --locked -- -D warnings
  -W clippy::perf -W clippy::suspicious`;
- `cargo test --workspace --exclude xray-rust-fuzz --all-targets --locked`;
- repository release/workflow/fixture-safety scripts;
- deterministic Go-oracle fixture verification;
- release-mode benchmark commands with reviewed raw provenance.

Tag CI additionally proves the pinned Xray-core interop matrix, bounded fuzz
campaigns, Apple/Android builds, supply-chain policy, secret scanning, and
source-only prerelease publication. Mobile tag CI proves the external Gradle
consumer, Apple source/artifact agreement, checksums, and prerelease channel.

## Acceptance criteria

RC4 is complete only when:

1. The three named XHTTP lifecycle regressions pass deterministically and no
   ambiguous partial request is replayed.
2. Fresh comparison results are published with exact current provenance, or a
   reviewed blocker explicitly prevents tagging.
3. Scheduled pinned and upstream-main early-warning jobs are present without
   changing the blocking release reference.
4. Roadmap/status/README/verification documents agree on implemented,
   deferred, and published state.
5. Core and mobile `v0.4.1-rc.4` prereleases exist, all required jobs pass, all
   assets and checksums verify, and no registry publication occurs.
6. Both repositories are clean at their annotated tags and the tags resolve to
   the exact reviewed release commits.

# Configuration tooling

Milestone E publishes an **executable configuration contract**: the generated
[machine-readable document](config-contract.json), the exact `xray-config`
parser, and CLI discovery/validation commands. This is the roadmap's permitted
equivalent to JSON Schema. It is not a standalone JSON Schema and must not be
registered with an editor as one. Key validity, external geodata, alias
precedence, conditional settings and aggregate budgets use the actual parser.
No second implementation of those rules is maintained.

## CLI

From this development checkout, build `cargo build --locked -p xray-cli` and use
`target/debug/xray-rust`. The commands below use `xray-rust` as shorthand for
that binary:

```sh
xray-rust config contract > config-contract.json
xray-rust config example vless-tls > client.json
xray-rust config check --config client.json
xray-rust config check --config client.json --json
cat client.json | xray-rust config check --config - --json
```

Examples are `socks-direct`, `vless-tls`, `xhttp-download` and `dns-routing`.
Their `.example` names, documentation addresses and UUID are synthetic; supply
your own endpoints and credentials before use. Example export never rewrites
an existing profile unless you explicitly redirect output to that file.

`check` accepts `-config` and `--config`. A path of `-` reads UTF-8 JSON from
stdin. It uses no TUN descriptor, changes no fd limits, starts no core, binds
no listeners, performs no DNS lookup and sends no network traffic. Local
geodata files are read on demand when the configuration references them.
Runtime environment variables such as `XRAY_TUN_FD` and `XRAY_TUN_PROFILE` do
not affect a parser check.

Resource lookup defaults match `run`: the config directory, working directory,
then executable directory, with duplicates removed. Stdin has no config
directory. To isolate validation from ambient databases, supply one or more
`--geodata-dir` flags; these form an exclusive, ordered search list:

```sh
xray-rust config check --config client.json --json \
  --geodata-dir ./profile-resources --geodata-dir ./shared-resources
```

A missing database/category fails with the original parser diagnostic and JSON
path. The tool does not download or substitute databases. Prefix filenames
beginning with `-` with `./` to distinguish them from options.

## Report contract

JSON mode writes exactly one report to stdout for accepted inputs, rejected
inputs and read/UTF-8 failures. These outcomes leave stderr empty. Usage and
output failures go to stderr. Exit codes are:

| Code | Meaning |
| --- | --- |
| `0` | Accepted by the parser; warnings may be present |
| `1` | Rejected by the parser |
| `2` | Invalid command arguments or input/output failure |

An accepted report has this shape (the core version follows the binary):

```json
{
  "schemaVersion": 1,
  "coreVersion": "0.6.0-dev.0",
  "scope": "parser",
  "valid": true,
  "diagnostics": []
}
```

Each diagnostic contains `severity` (`warning` or `error`), `path` (a JSON-path
string or null), and `message`. Read failures use `scope: "input"`,
`valid: false` and an error at `$`. Consumers must check `schemaVersion` and
`scope`; human-readable messages are not stable error codes. Warnings preserve
compatibility decisions such as deprecated `qtype` and removed
`scMaxConcurrentPosts`, and do not change the success exit code.

Reports contain no normalized config/model dump. They preserve existing parser
diagnostics, including encryption-value redaction. Other diagnostic messages
and dynamic JSON paths can contain input such as tags, domains or unknown keys;
treat reports as profile-related data rather than public telemetry.

`valid` means **parser acceptance**, matching the same parser and resource
directories used by the embedding. Core graph/carrier compilation, socket
binding, host VPN policy and network availability are subsequent checks. For
example, missing outbound targets, cycles, some Vision/carrier combinations,
and nonempty QUIC UDP hopping are rejected later by core compilation. An empty
model is currently parser-valid. Tooling preserves this behavior rather than
silently changing load semantics.

## Machine-readable discovery

`config contract` emits `kind: "xray-rust-executable-config-contract"`, tooling
version, linked core version, validation instructions, recognized grammar
objects, additional dynamic/compatibility surfaces and canonical examples.
The checked-in [document](config-contract.json) is generated by:

```sh
cargo run --locked -p xray-config --example config_contract > docs/config-contract.json
```

`objects[].fields` lists recognized keys, including restricted and ignored
keys. It is not an unconditional allowlist. Each grammar node is shared with
the parser's unknown-field check; its `context` identifies the consuming
location, and `notes` describes the main restrictions. The executable checker
decides whether that node is active and whether its values and combinations
are accepted. `additionalSurfaces` records maps, XHTTP download composition and
existing ignored input such as `log`, extra TUN settings and additional REALITY
fields. Ignored input is not advertised as working runtime behavior.

An editor can use the document for discovery and starting examples, then invoke
the stdin JSON checker for authoritative diagnostics. Use a binary and contract
from the same core release. Future field/value changes update the generated
document and fixtures with the parser; tooling-envelope versioning is separate
from the stable C ABI.

Rust integrations can call `xray_config::tooling::configuration_contract()` and
`validate_xray_json`, `validate_xray_json_with_geodata_dirs`, or
`validate_xray_json_with_exclusive_geodata_dirs`. An empty exclusive directory
list disables geodata search. These APIs return diagnostics and dispose of the
parsed model without exposing it in a report.

## Maintenance and verification

`surface.rs` owns the 41 recognized object-key sets used by parser rejection
and contract generation. `parser/dns.rs` owns DNS clients, hosts, fake IP and
DNS outbound rules; `parser/stream.rs` owns stream/carrier/security selection.
They join the previously extracted routing, VLESS and XHTTP modules. This
increment preserves parsing behavior and changes no C ABI symbols, layouts,
minor version, capability bits or Swift/Kotlin projection.

Ordinary CI runs the contract snapshot guard, shared accepted/rejected fixtures,
an unknown-key mutation at every registered grammar node, existing VLESS/XHTTP
oracle fixtures, and process-level CLI tests including geodata isolation and
exit codes. It publishes the validated contract and this guide as an artifact;
both also ship in source archives. Reproduce the focused checks with:

```sh
cargo test --locked -p xray-config -p xray-cli --all-targets
cargo clippy --locked -p xray-config -p xray-cli --all-targets -- -D warnings
```

The existing CLI runtime tests need permission to bind loopback sockets; the
configuration commands themselves do not. Broader TUN, runtime DNS and FFI
module splits follow their next feature as required by the roadmap. Final
candidate device/performance evidence and release review remain separate gates.

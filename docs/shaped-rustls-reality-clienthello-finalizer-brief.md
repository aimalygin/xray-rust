# shaped-rustls Brief: REALITY ClientHello Finalizer Hook

## Goal

Add a shaped-rustls ClientHello hook that lets xray-rust implement Xray REALITY with a single ClientHello lifecycle:

1. rustls builds the real ClientHello once, including real active key exchanges such as `X25519MLKEM768`.
2. xray-rust inspects the encoded ClientHello while the legacy session id is still zeroed.
3. xray-rust derives the REALITY auth key, seals the 32-byte REALITY session id, and patches those bytes into the same ClientHello.
4. rustls uses the patched ClientHello for both the TLS transcript and the bytes written to the network.
5. The same active key exchange state continues the handshake.

This should mirror the uTLS/Xray model: `BuildHandshakeState()` creates one `Hello.Raw`, Xray patches it, then the same handshake state continues.

## Problem In Current API

xray-rust currently uses shaped-rustls roughly like this:

- `ClientHelloCustomizer` returns a `ClientHelloPlan`.
- `ClientHelloPlan` can set fixed random, fixed legacy session id, fixed X25519 material, extension ordering, raw key shares, ECH/ALPS/grease/padding, and `CapturesClientHello`.
- `CapturesClientHello` can observe the final encoded ClientHello bytes, but it cannot replace or mutate them.
- xray-rust therefore generates a zero-session-id ClientHello for REALITY preparation, computes the sealed session id, then generates another ClientHello with the sealed session id for rustls to actually use.

That "generate twice" model only works while all generated ClientHello bytes are deterministic. It fails for real hybrid/PQ key exchange:

- If `X25519MLKEM768` is represented as a raw zero-filled key share, the ClientHello shape matches Go/uTLS but the key share is not cryptographically valid.
- If `X25519MLKEM768` is generated by rustls/aws-lc as a real key exchange, the ML-KEM part is fresh per generation, so the prepared ClientHello no longer matches the ClientHello used by the rustls transcript.

The correct fix is not to make ML-KEM deterministic. The correct fix is to let xray-rust patch the single ClientHello that rustls is about to use.

## Required Hook Semantics

Add a hook that receives the final encoded ClientHello handshake message and may return replacement bytes before rustls adds the ClientHello to the transcript and before rustls writes it to the network.

Important details:

- The hook input should be the encoded TLS handshake message, not the outer TLS record.
- The hook must run after all ClientHello shaping has been applied, including real key-share generation and padding.
- The hook must run before the ClientHello is committed to the transcript.
- The hook must run before the ClientHello is written to the peer.
- The hook must preserve rustls' active key exchange state; it must not force ClientHello regeneration.
- The hook should be able to fail the handshake with a normal rustls `Error`.
- For xray-rust's immediate REALITY path, TLS resumption is disabled, so `pre_shared_key` binder support is not required for the first implementation.
- If this hook is later allowed with PSK binders, the final session-id bytes must be included in binder computation. A hook that mutates the ClientHello after binder finalization would invalidate binders.

## API Shape Suggestion

This is only a suggested shape; use whatever fits shaped-rustls style best.

```rust
pub trait FinalizesClientHello: fmt::Debug + Send + Sync {
    fn finalize_client_hello(&self, bytes: &[u8]) -> Result<Vec<u8>, Error>;
}

impl ClientHelloPlan {
    pub fn with_finalizer(self, finalizer: Arc<dyn FinalizesClientHello>) -> Self;
}
```

Alternative signatures are fine, for example:

```rust
fn finalize_client_hello(&self, bytes: &mut Vec<u8>) -> Result<(), Error>;
```

The important contract is that the bytes after finalization are exactly the bytes used for the transcript and network write.

## xray-rust REALITY Use Case

xray-rust needs the finalizer to:

1. Parse the ClientHello.
2. Verify the legacy session id is 32 bytes and currently zeroed.
3. Extract `hello.random`.
4. Locate the X25519-compatible public key:
   - plain `X25519` key share, or
   - the X25519 component inside `X25519MLKEM768`.
5. Derive the REALITY shared secret using xray-rust's local REALITY private key and the server public key.
6. Derive `auth_key = HKDF-SHA256(shared_secret, salt = hello.random[..20], info = "REALITY")`.
7. Seal the 32-byte REALITY session id using Xray's AES-GCM construction, with the zero-session-id ClientHello bytes as associated data.
8. Patch the sealed session id into the legacy session id field.
9. Store the `auth_key`, sealed session id, and final ClientHello bytes for REALITY certificate verification.
10. Return the patched ClientHello bytes to rustls.

The finalizer must be able to share derived metadata back with xray-rust's certificate verifier. This can be handled by xray-rust using shared state around the finalizer; shaped-rustls only needs to call the finalizer before transcript/write.

## Acceptance Tests Needed In shaped-rustls

Add tests around shaped-rustls itself, not xray-rust:

1. A finalizer that flips or patches a known byte in the ClientHello causes the captured/written ClientHello bytes to contain that patch.
2. The TLS transcript uses the patched ClientHello, not the pre-finalized bytes. A practical test can complete a local client/server handshake where the server observes the patched ClientHello and the client finishes successfully.
3. The finalizer runs after normal shaping controls: fixed random, fixed session id, extension order, raw/exact extensions, padding, and key-share generation.
4. The finalizer runs with real `X25519MLKEM768` active key exchange and the handshake can still complete with a server that selects `X25519MLKEM768`.
5. If the finalizer returns an error, the handshake fails cleanly and does not write a partial ClientHello.
6. If PSK/resumption is enabled and binder support is not implemented, the API should either reject finalization with binders or have an explicit documented ordering that keeps binders valid.

## Acceptance Tests Expected In xray-rust After This Hook Exists

xray-rust should then add tests that prove:

1. For `chrome` / `hellochrome_133`, the `X25519MLKEM768` key share has a real non-zero ML-KEM component.
2. The embedded X25519 component still matches xray-rust's prepared REALITY private key.
3. The finalizer patches the sealed REALITY session id into the exact ClientHello that rustls writes.
4. The ClientHello bytes used for ML-DSA-65 certificate verification are the patched bytes used by the rustls transcript.
5. The old shape oracle still reports parity with Go/uTLS for all supported fingerprints, but shape parity is not treated as proof of key-share validity.

## Non-Goals

- Do not make ML-KEM deterministic just for REALITY.
- Do not expose rustls private key exchange internals to xray-rust.
- Do not require xray-rust to serialize ClientHello by itself.
- Do not make `CapturesClientHello` mutable if a separate finalizer hook is cleaner.
- Do not require PSK binder support in the first slice, as xray-rust disables resumption for REALITY.

## Why This Is Preferred Over Deterministic Hybrid Key Exchange

Deterministic or saved hybrid key exchange would only fix one source of non-determinism. The broader REALITY requirement is that the ClientHello used as AEAD associated data, the ClientHello in the TLS transcript, and the ClientHello written to the peer are the same bytes.

A finalizer hook makes that invariant explicit and supports future ClientHello features without requiring xray-rust to replay rustls' internal randomness.
